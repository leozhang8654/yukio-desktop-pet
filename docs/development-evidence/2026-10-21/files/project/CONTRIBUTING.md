# 提交、PR 与开发记录规范

2026-10-18 建立，适用于后续 Yukio 开发。历史提交不改日期、作者，不重写已推送历史；不足的说明通过新文档和链接补充。

## 每次开发如何留下记录

1. 先写清用户遇到的问题、预期变化与范围。为相关改动选择一个主题，保留无关本地工作。
2. 实现后记录真实验证对象：源码提交或候选文件哈希、操作系统、方法、结果、跳过项及未覆盖范围。模拟接收、原生窗口、真实服务往返分别描述。
3. 用户可感知变化先进入 [CHANGELOG 的“未发布”](CHANGELOG.md)。有公开 Release 后才写“已发布”，日期使用 Release 的 UTC `published_at`；候选版本号不自动成为正式版本。
4. 有意义的里程碑更新 [开发过程记录](docs/development-log.md)，按“问题 → 修改 → 验证 → 结果 → 下一步”归纳。小修复可并入对应阶段，不逐条复制 Git 日志。
5. PR 使用 [默认模板](.github/pull_request_template.md)。标题和正文以最终改动为准；若范围改变，更新说明，保留仍有意义的失败与取舍。
6. 仅在任务要求交付／发布时核对目标分支、公开包、下载哈希与桌面运行版本。文档任务不触发构建、发布或更换 App。

## 状态与证据口径

| 用词 | 最低依据 |
| --- | --- |
| 计划中 | 有需求或设计，未声称实现 |
| 进行中 | 已开展，目标尚未实现 |
| 已实现 | 可定位源码、资源或可运行候选，不代表已测试 |
| 已验证 | 标明对象、环境、结果和未覆盖范围的检查记录 |
| 已发布 | 有真实公开 Release 与相应可下载附件 |
| 受阻 | 有具体阻塞条件、影响范围及解除所需条件 |

“待验证／待核实”用于缺少证据的字段。避免一个“完成”概括实现、测试、发布、安装和实际运行；不编造完成百分比。测试计数必须来自当次输出，写清总数、跳过数和平台。Windows 原生结论必须来自 Windows 环境；在 macOS 上用 Win32 替身测试不能替代它。通用 Mac 二进制不等于 Intel 已实跑，角色缩放倍率不等于系统 DPI 覆盖。

历史补记注明整理日期和依据，原始日期未知时写“未找到记录”。公开证据使用固定提交、PR、Actions run／attempt、报告和版本化 Release 链接；不得将会变化的 `latest` 当作历史版本证据。报告应记录失败尝试及后续修复，不用成功重跑删除失败。

## 提交模板

标题建议：`类型(范围): 具体对象与改变`。类型可用 `feat`、`fix`、`docs`、`test`、`build`；范围如 `answers`、`motion`、`windows`、`updates`。不要求为已有提交补改格式。

```text
fix(answers): 读取 canonical history，避免将活跃问题误判为过期

问题：<触发条件；此前用户看见的行为>
修改：<现在的行为；关键方案与采用原因>
验证：<实际运行的方法、系统、结果；证据位置>
限制：<跳过或未覆盖的场景；没有就按实写>
关联：<Issue / PR / 报告 / 阶段记录；不存在则省略>
```

上面的标题仅示范格式，不代表新增了该修复。简单文档修订可只写清改动与链接检查，不填写无关平台测试。

## PR 正文模板

GitHub 会加载仓库中的 [PR 模板](.github/pull_request_template.md)。核心内容如下，可删除不适用项，不用空泛勾选代替证据：

```markdown
## 问题与变化

<什么条件触发问题？修改前后用户看到什么？>

## 方案与范围

<修改对象、关键选择及原因；与本任务相关的兼容性和取舍>

## 验证与限制

| 对象 / 源码 | 环境 | 方法与实际结果 | 证据 / 未覆盖 |
| --- | --- | --- | --- |
| <提交或候选哈希> | <系统及是否真实原生> | <检查、通过/失败/跳过> | <报告或运行链接；限制> |

<失败尝试及处理；未运行的检查明确写未运行。>

## 交付状态

- 源码：<本地已实现 / 已推送 / 已合并；链接>
- macOS / Windows：<各自验证状态；不适用可省略>
- 公开包：<未发布 / Release 与 SHA-256 入口>
- 桌面运行：<未检查 / 已核对的版本、来源与时间>
- 后续：<待验证事项或具体阻塞>

## 关联记录

<阶段记录、CHANGELOG、Issue（如有）；没有 Issue 不编造编号。>
```

## 阶段记录模板

```markdown
## <阶段目标>（<有证据的时间范围；未知则注明>）

整理日期：<YYYY-MM-DD>。依据：<提交 / PR / 报告>。
状态：<计划中 / 进行中 / 已实现 / 已验证 / 已发布 / 受阻>；<状态适用范围>。

**问题。**<用户问题、触发条件与背景，不补造用户反馈。>

**修改与选择。**<做了什么、前后变化、为何采用该方案。>

**验证。**<被测提交或资源哈希、平台、方法、实际结果、跳过项。>
<失败尝试 → 发现 → 修复或仍未解决；客观记录，不隐藏返工。>

**结果与限制。**<实现、验证、发布、桌面安装分别说明；缺证据写待核实。>

**下一步。**<剩余场景和解除阻塞条件；没有依据不写预计完成日期。>

**证据。**<固定提交链接、PR、源码、Actions attempt、报告、Release。>
```

## 公开记录前检查

只纳入本任务相关文档；检查暂存内容，避免把已有源码、生成素材、聊天日志、个人路径或密钥混入提交。需要引用本地实验时，先另存脱敏报告，不把整目录视为可公开附件。缺失原件或链接失效时明确标记，不把不存在的路径包装成证据。

这些记录用于解释和追溯过程，不是对作者身份、原创性或投入工时的独立证明。
