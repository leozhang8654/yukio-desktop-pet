## Stage 1.1：调用结果关联

**Technical Reasoning。** 用每个解析器独立的有界关联状态替换单个 `pendingFailure`。有显式调用引用或与已知调用相同的条目 ID 才建立联系；不使用时间邻接、工具名或正文相似度。明确区分本条回执的 `outcome` 与当前关联窗口汇总的 `call_outcome`。结果记录独立于 `PetEvent`，防抖或动画结束不会变成成功证据。

**Beginner-Friendly Explanation。** A 和 B 同时做事时，失败回执必须贴到有对应编号的那件事上。没有编号就单独留着，不能贴给下一位。收到一张回执只说明收到了消息，消息里明确给出成功依据才能说成功。相互矛盾的回执也不能任取一张。

### Implemented

- Swift 与 Python 同步修复两种错误：A 的失败被 B 消费；B 开始使 A 的失败被清除。
- 新增 `CodexToolResult` 元数据：会话、轮次、调用、条目、原始状态、条目类型、结果、退出码、关联方式与冲突标记。
- 成功、失败、取消、未知分别表示；取消优先于退出码 130；`completed` 单独不证明成功。支持旧式 JSON 回执和明确的 MCP `isError` 字段，不扫描普通正文猜结果。
- 显式轮次隔离；旧轮次的回执不能改变当前调用。未带轮次但已发现调用 ID 重用时隔离为 `ambiguous_reused_call`。没有捕获当前轮次上下文时，不把显式其他轮次的结果混入当前窗口。
- 缺少调用身份的输出不能再关闭路由器最后一个无关调用；异步问题的 `accepted: true` 仍仅表示展示确认。
- 每个解析器保留最近一条输入的 `lastToolResults` / `last_tool_results`；新增只读 `--codex-results` 诊断导出，包含来源行号、行字节 SHA-256 和时间是否存在，不导出消息、命令、参数或结果正文。
- 活动与历史的持久化尚未接入。实时来源依然消费桌宠事件；新元数据目前通过解析器接口和诊断导出可用，不会自动形成后台历史库。

### Issues

- 本地与公开发布基线不同，不能直接用此工作区覆盖正式安装。
- 无身份关系的内层失败仍可导出为“未关联失败”，不会冒充外层失败；当前桌宠因此可能不显示这类内层失败。后续工作台需要直接展示这些证据。
- 迟到回执会出现在结果证据中，现有桌宠路由器不会追溯重演已经结束的动画。`activity_end` 仍是显示层回执，不能用来判断成功。
- 活跃关联和已退出调用 ID 窗口分别限 4096 条；无持久化、无全历史去重。超过窗口的关联只能退化，不能宣称任意长期乱序或 ID 重用均已解决。
- 没有源轮次时，`current_context` 是解析上下文归属，`unavailable` 是未取得；都不是上游显式身份。没有源时间戳时诊断中标记不可用，不应把数值 0 当作真实发生时间。
- 结果状态只表示所识别回执报告的操作结果，不证明文件实际效果、整个任务达标或用户验收。
- 诊断流是按原始顺序的逐条解释，包含重复回执；来源行指纹不是全局事件 ID，也不提供历史修订数据库。

## 本地复验

在仓库根目录执行：

```sh
swift test --package-path YukioPlayer
(cd YukioWin && python3 -m unittest discover -s tests)
python3 tests/verify_codex_result_parity.py
```

只读检查指定的 Codex JSONL（输出仅到本机终端）：

```sh
YukioPlayer/.build/debug/YukioPlayer --codex-results /path/to/session.jsonl
(cd YukioWin && python3 -m yukio --codex-results /path/to/session.jsonl)
```

导出每行最多 8 MiB；输入不合法时非零退出，可能已输出此前有效记录，调用者必须检查退出码。该诊断不会重跑工具、发送回答、访问千问或打开第二只桌宠。
