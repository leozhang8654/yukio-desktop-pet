# 给执行 AI：千夏十二状态动画底图优化任务书

版本：2026-10-10 / v2。用途：用户将本文件与现有十二张透明 PNG、角色参考一起交给具备图像编辑能力的 AI 或执行代理，用于优化现有动画底图。本文件可独立使用，不依赖旧报告或历史聊天。

## 0. 先理解任务，再动图

你是角色美术与动画底图精修助手。任务是对现有千夏桌宠的十二张 AI 生成底图进行局部优化，保留已经选定的角色、科幻设备、姿态、工作含义和透明构图。

产品目的：用千夏与她的科幻工作设备展示 AI 正在进行的工作，并提供适合长期放在桌面的陪伴。设计要好看、耐看、实用，复杂度应服务桌宠的实际展示与动画。

采用 A 方向：轻科幻日常桌伴。“轻”指观看与运动负担适度，并不要求设备数量减少或让人物永远比设备突出。

App 的 task bubble 将解释准确的当前行为。人物、设备、主符号、动作和 task bubble 共同表达状态。主符号可以是理解的主要入口，目光与动作可以引导观看，大形和手势同样重要。

本轮产物是优化后的静态透明底图，以及如实记录的检查材料。动画编码、程序改动、正式资源替换、安装和发布不属于本轮产物。

## 1. 用户已确认的设计选择：执行时必须保留

- 保留科幻装备的身份与叙事价值。它们本身就是桌宠的一部分，不把“像小工作站”当成必须消除的问题。
- 不强制让脸或手势永远成为唯一主体。设备、符号可成为当前工作的主要视觉重点。
- 不强制把所有主符号改到固定位置。保持符号与所属道具、投影、手势的关系。
- 思考状态中的问号允许保留；等待回应状态中的问号也保留。task bubble 会解释不同上下文。
- 保留读文件的三张全息文件卡与浏览网页的扇形多面板概念。不要默认合并为单屏。
- 保留验证探针与模块、透光检查台与检查笔、分体键盘、轨迹球控制台、电子明信片。
- 保留完成状态的埋头休息、脸部被遮挡和对号牌。遮脸是有意姿态。
- 保留当前透明桌前场景、完整前挡板、桌椅支撑与自然露出的双腿。不能因“人物优先”裁切、隐藏或改变这些已选内容。
- 已经正确的区域和状态可以不改。不以修改数量证明完成工作。

如果接触到初版报告，其中“思考删除问号”“三屏合并单屏”“强制人物第一”“全状态统一信号位置”“验证改传统清单”等建议已被本次用户反馈覆盖，不再执行。

## 3. 修改决策规则

优先级：用户的最新明确反馈 ＞ 本任务书 ＞ 本轮各状态已确认底图的姿态与设备 ＞ 原角色设定的身份参考 ＞ 历史建议。

编辑前，每项修改写明：状态、可见位置、具体问题、证据、最小修法、预期影响。不要只写“更精致”“更高级”“更像桌宠”。

问题级别：

- P0：违背保留项、角色变样、透明背景丢失、明显多手少手或关键设备缺失、错误穿插、画布被裁断。候选直接退回。
- P1：实际可见的接触断裂、符号变形、桌椅透视冲突、跨状态意外漂移、透明污染、无法支持既定动作的连接结构。优先局部修复。
- P2：局部高光拥挤、冗余细线、光晕压住符号、材质层次混乱。仅在能指出问题的区域精修。
- 偏好或不确定项：例如想换道具、重排多面板、改变表情性格、显著改变设备体量。先保留原设计，记录备选理由；确实需要扩大范围时再向用户提出具体选择。

任务内的常规局部修复直接完成，不逐笔请求确认。不得为了让十二张“都有优化”而重绘已经正确的部位。

## 4. 全局锁定项

### 4.1 人物身份与画风

保持浅黄绿色头发、马尾及蓝色蝴蝶结、左右不对称发夹、眼睛配色与略慵懒的气质、粉白服装、领带、深紫结构色、圆润软袖与鞋子特征。

以当前源图的头身比例、脸型、描边和阴影风格为基准，避免精修后出现新脸、肤色漂移、眼睛变大、头部变圆、年龄感改变、服装缩水或装饰随机增减。可修复实际画错的身份细节，不随意重设计。

不增加背景海报、标题、品牌标语、边框、水印、复杂舞台或装饰粒子。原角色设定图的排版和文字不属于透明桌宠底图。

### 4.2 构图与系列一致性

保留源图画布尺寸和长宽比，不拉伸。展示预览使用 192 × 208 的目标画框并等比例适配；先检查源图比例与透明留白，不将预览像素当成编辑原图分辨率。

记录桌沿、桌脚、椅子、摆件、箱子、人物头部和脚部位置；检查固定场景是否意外漂移。跨状态固定部分可复用同源底层或确定性合成，使其一致；复用之前必须明确当前哪些差异是有意状态变化，不能把趴桌等不同姿势硬套同一轮廓。

不默认把待机图当成所有状态的主标准。选择哪张作为某个共享元素的基准，应依据现有确认记录、透视和完整度；没有依据就记录待定，不在全部图中传播可能错误的版本。

### 4.3 科幻装置与视觉层次

保留各状态主要设备、投影数量、功能隐喻与布局概念。允许设备成为视觉中心，允许合理遮住衣服或手臂。需要修复的是错误穿插、无意义遮挡和关键交互被掩盖。

保留实体外壳、透明投影和发光符号的材质区别。设备结构可以精简无意义碎线，但不抹平体块、删除有用面板或削弱科技气质。

主符号清楚即可，不通过整块屏幕大幅提亮来提高可读性。先尝试局部底色、笔画、间距和有限的明暗调整，不统一提高所有区域对比。

### 4.4 透明度和边缘

交付真实 alpha 透明 PNG，保留源图有意的半透明投影和光晕。检查白、深灰、黑、洋红与棋盘格背景。不要绘制假棋盘格，不把白衣／高光当作背景，不全局腐蚀、膨胀或模糊掩盖边缘问题。

背景 alpha、人物抗锯齿与投影半透明是不同问题。保留干净深色描边，不加统一粗白轮廓，不以全图变透明降低存在感。

## 5. 每个状态的独立编辑指令

执行每一条时，同时使用第 1、3、4 节约束。下列“检查”是待核实项，不代表原图已经被认定有错；正确则保留。每次只绑定对应状态原图，不凭其他状态重造。

### 01 / idle / 待机

保留磁悬浮球、底座、手指轻拨的关系和原姿态。球体悬浮属于设定，不能把球粘到底座上。检查球与底座的空间对应、手指朝向与球面接触意图、底座在桌面的落点。仅修定位偏差、错误手指或压住球体轮廓的过亮光晕；保留球体图案与科技质感。

后续动画预留：手、球与底座可分别控制，底座固定。不在静态底图里添加运动轨迹、重复球体或拖影。

### 02 / thinking / 思考

保留托腮、节点图投影和原有问号。检查托腮手与脸的接触是否成立、节点分支是否断裂或无意义纠缠、问号是否完整、投影和袖子遮挡顺序是否合理。只清理真实碎线和光晕污染，不移除问号，不改成纸本笔记，不把节点图搬到统一提示区。

后续动画预留：头颈与托腮主体稳定，眼睛可扫视节点。无需新增头部摇动。

### 03 / read_file / 读文件

保留三张全息文件卡、当前排列和交叠双手。文件夹或文档符号可以成为主阅读线索。检查三卡平面、边框厚度、前后遮挡、符号一致性和卡间距。若边框光晕使符号模糊，局部收敛光晕或修清笔画；保留通透感与三卡布局。

不强制与浏览网页形成完全不同的大形，不以易混为由合并成单卡。精确状态由 task bubble 解释。

### 04 / view_image / 看图片

保留透光检查台、朝向角色的图片和检查笔。让图片中的图形轮廓在目标尺寸仍能作为图像线索。核对笔尖指向的检查区域、握持手指、检查台与桌面透视。保留“正在查看／检查”的关系，避免新增连续笔迹把行为改成绘画。

不默认换成放大镜，不为了观众阅读把台面或图片翻转到不合理角度。笔与手为未来联动单位。

### 05 / write_file / 写文件

保留分体键盘、双手、中央设备及原工作姿态。检查指尖与键帽、手腕与袖口是否连接自然；两侧键盘的透视与落点应属于同一桌面。仅清理太密而不可读的键帽线、错位按键和失真的代码图形。

不合并成传统单键盘、不改成写字、不新增满屏代码。保留两手可错开敲击的空间，避免把手与设备生成成连体块。

### 06 / verify / 验证

保留诊断探针、被测模块和检查含义，科幻硬件隐喻可以表达 AI 验证工作。检查探针笔身、握持、尖端与目标测试点是否对应，模块体块与桌面接触是否可靠，原有诊断图形是否清楚。

不因“像维修”改成纸张核对，不给正在验证的图随意添加“全部通过”或成功对号。检查动作目标清楚即可，准确工具名称由 bubble 解释。

### 07 / read_web / 浏览网页

保留扇形链接面板、原面板数量与展开方式、地球及链条主符号。核对各面板的角度、投影来源与前后关系，修复链条断裂、地球经纬线失真和不必要的伪文字。让点按手指指向原定面板区域。

不删除侧面投影，不为了区别读文件强制变成单横屏。不新增浏览器品牌或网页正文。投影应维持稳定的科技质感。

### 08 / default_work / 工作中

保留轨迹球和朝向角色的显示器。检查手掌是否自然包覆或接触球体、指节数量、显示器外壳和支架透视、底座在桌面的支撑。显示器遮挡部分衣服属于可接受构图，只在遮挡存在实际错误或妨碍关键操作时做最小调整。

不翻转显示器面向观众，不为了露脸默认缩小整套设备，不强行露出被设备合理遮住的完整手臂。

### 09 / respond / 回答

保留电子明信片、信封符号和轻微递交姿态。检查持卡手指、卡片边缘和透视，信封符号应完整并附着在同一平面。适度保留电子质感，避免光晕覆盖握持边缘。

不把实际回复文本或任务 bubble 画进卡片，不增加全屏消息流。手与卡片应能作为一个稳定的联动组。

### 10 / task_complete / 完成

保留埋头趴桌、脸部被遮住、柔软袖子与对号牌。检查额头／头发／袖子的层次、手臂与桌面接触、桌面是否因趴姿意外变形、对号笔画和牌面是否完整。

不抬头、不露眼、不改微笑表情、不改举牌、不删除对号。底图不负责实现未读确认逻辑；该逻辑交给 App。不要凭空添加鼻子、嘴或被遮住的眨眼层。

### 11 / question_for_user / 等待回应

保留呼叫按钮、手指轻按关系和全息问号气泡。检查按钮顶面与底座的透视、手指落点、袖口连接、问号轮廓及气泡与装置的空间关系。

此处问号和思考问号都合法。不要求问号专用或统一位置；不在图片上加“等你回答”字样，准确文字由 App 渲染。给未来短行程按压留出合理空间，不先画成多重手指或多层重影。

### 12 / failed / 遇到问题

保留故障数据卡、警告三角／叹号与轻微失落的表情。检查警告符号有没有变成杂乱线条、卡片与握持是否一致；在必要时局部改善卡底与符号的明暗区别。

不夸张哭泣，不增加泪流、爆炸、红色闪屏或损坏设备的戏剧场景。保留温和陪伴气质，不把一次工作问题画成角色遭受伤害。

## 7. 推荐执行流程

### 7.1 基准与检查

新建本轮目录，保存原图清单、角色参考、任务书和输入哈希。制作十二图对照页，分别看原尺寸和至少 200% 放大。记录每张实际问题；把没有问题的项标记为保留。

为每张计划修复的图片准备允许变化区域。区域大小来自实际问题，不凭未知坐标写固定矩形。已验收的同图蒙版优先复用；不存在则按需要建立，不默认重新分割全套素材。

### 7.2 校准和批量精修

从有明确问题、又能代表主要画风的一张开始，验证局部编辑能保持原风格与 alpha。随后沿同一标准完成其余状态，逐张关联问题编号。无需把第一张的姿态复制到所有状态。

每轮只处理一组相关问题，例如手与探针、符号与光晕、桌沿与透视，避免一次改太多失去因果依据。生成模型若改动了外部区域，应通过编辑蒙版与确定性合成还原锁定区，并再次检查接缝。若当前工具无法完成锁定与检查，输出候选并标明未验证，不把它当成正式成品。

不把数次失败理解为必须不断重生。相同问题再次发生且无法定位时，保留失败证据，改变局部处理方法或说明缺少哪种编辑能力。

### 7.3 同尺寸与多背景验证

保存并重新打开最终 PNG，不只看生成工具缩略图。检查源图尺寸、透明通道、主体留白、描边和所有有意半透明区域。

制作原图／候选并排与差异图；在白、深灰、黑、洋红、棋盘格上检查边缘，在文档、编辑器和复杂壁纸示意上检查整体。检查 192 × 208 等比例预览以及目标系统缩放，不只用大图评价。

允许变化区域外比较所有可见像素和 alpha。完全透明像素的不可见 RGB 可单独忽略，但不能忽略 alpha 改变或半透明区域改变。若没有像素比较工具，标记此项未测。

### 7.4 与 task bubble 一起检查

若有真实界面参考，按同一 bubble 文字与相同位置比较原图、候选：画面是否支持文字表达、设备有没有被 bubble 意外盖住、整体是否拥挤。不要同时改文字和底图后把全部改善归功于画面。

若只有示意，可用另存的示意页检查空间关系，显著标明“task bubble 示意，非实际 App 验收”。不要把示意文字合成进透明底图。无 bubble 的图只检查合理性，不强制实现十二状态盲辨。

## 8. 为后续动画准备的要求

本轮只保证可见底图与结构；不宣称静态图已经有分层、枢轴、眨眼或循环。

如果同时制作分层，需要按实际运动关系处理：手与握持道具联动；球体、投影、按钮、眼睛可按设计独立；固定袖口、桌沿和前景用作遮挡。移动后露出的衣服、桌面或背景要有对应补底，不保留原位置的残手、笔杆和影子。

外背景透明与内部部件分割分开。已有真实透明和最终蒙版优先保留；只有新增部件或明确选区缺陷才需要新分割。SAM 2.1 只负责初选，使用前核实模型和入口，不能把自动分割直接当成最终验收。

单实体手部可检查连通与漏选，但多片投影、真实开孔、分离的光晕可能合理；记录语义预期，不把所有部件硬套“一连通零孔洞”。允许变化区域不是实体部件，不能用相同拓扑标准。

沿用当前方案的头颈与家具固定、独立眨眼、小幅手部动作。完成状态遮脸，不凭空增加眼睛层。新底图的实际分辨率与眼皮结构需核实，不机械套用旧角色的尺寸或六级眼皮参数。

如后续真正制作动画，再检查最大位移、接触、补底、预乘 alpha、编码回读与每状态至少三个真实速度循环。该动态验收不由本轮静态检查替代。

## 9. 验收清单

每项写“通过／失败／未测／不适用”，附实际证据或原因。没有打开图片不能写“目视通过”，没有测试不能写“独立评审通过”。

- 意图：科幻装备、原主符号和各状态创意保留；两处问号保留；没有强制多屏改单屏、人物唯一主体或统一提示位置。
- 身份：脸、发色、发夹、蝴蝶结、服装与比例未意外改变。
- 工作关系：手、设备、目光和符号方向合理；允许有意悬浮，不允许错误穿插。
- 局部改善：每个改动对应已记录问题，有原图和候选证据；未制造新的缺陷。
- 系列：固定场景的意外漂移已检查；有意姿态差异保留。
- 技术：尺寸和长宽比符合输入约定，背景真实透明，投影半透明保留，描边和白衣未误删。
- 锁定区：允许变化范围外可见像素与 alpha 的对照结果有记录；未测时不声称完全一致。
- 实际大小：192 × 208 预览中符号与设备关系清楚，细节没有只在放大时成立。
- 界面：与真实 bubble 共同观看的结果单独记录；没有真实 UI 时标记未验证。
- 动画准备：接触点与部件边界适合既定动作；未制作的补底、分层和动态项明确列出。

通过静态验收的底图仍可能需要后续原生播放验证。不能宣称通过 macOS 或 Windows 实机测试，除非确实在相应环境执行。

## 10. 交付格式

推荐新目录结构；它是交付约定，不代表这些文件已经存在：

```text
qianxia-refine-R01/
  input-manifest.json
  source/                 原始十二张 PNG 与角色参考
  candidates/             本轮十二状态；未改者可保持原文件内容
  edit-regions/           实际编辑蒙版或可定位的范围记录
  review/                 同尺寸并排、差异、多背景与十二图对照
  prompts/                每次实际使用的提示词与参数
  changes.md              每张问题、修改、保留与失败记录
  qa.json                 状态、检查结果、证据与未测项
```

每张状态记录至少包含：state_id、输入文件及哈希、原始尺寸、实际问题、允许修改范围、保持项、输出文件及哈希、是否有改动、静态检查、UI 检查、动画准备情况、未解决项。工具不支持某字段时写 null 并说明，禁止捏造数值。

结尾向用户汇报：实际修改了哪些状态和部位、为什么符合本任务、哪些保留未动、哪些检查确实完成、仍需哪些后续工作。不要把生成了十二张图片等同于十二张都通过。

## 11. 交付前最后一次自查

逐项问自己：我是否仍在优化这套千夏底图？科幻装备是否仍完整讲述原来的工作？我有没有为了旧报告的主观偏好删掉面板或问号？有没有让 task bubble 承担它本来就负责的精确信息？有没有在没有缺陷证据的地方随意换脸、改姿态或降色？我提供的检查结论是否来自实际文件？

最终成品应让用户认出同一位千夏、同一套创意和设备，只看到已经定位的问题被修好，以及更稳定、更耐看的系列质量。
