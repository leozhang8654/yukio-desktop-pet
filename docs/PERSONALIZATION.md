# Yukio：行程、活动记录与个性化助手设计

更新：2026-09-25。本文记录产品方向和建议方案，不代表功能已经实现。本轮只更新设计，不接入 API、不开启屏幕观察。

## 产品方向

用户把目标、每日行程和感兴趣的事情交给 Yukio。助手结合行程和用户允许观察的电脑活动，选择合适的时机提醒，并逐渐积累用户可以查看、纠正、删除的个人记录。桌宠承载轻量交互，主窗口管理安排、记录和偏好。

用户已明确希望支持：

- 接入 AI API，让助手理解自然语言和当前内容。
- 根据持续一段时间的活动触发提醒，例如计划学习物理，却持续在电脑上处理无关内容。
- 输入每日行程，让提醒随每天的安排调整。
- 支持自动记录和手动维护；用户启用后，应用运行期间能够自动观察并记录活动。
- 自动生成的个性化内容可以被用户查看、修改和纠正。
- 后续支持每日新闻和兴趣话题简报。

下面的页面组织、提醒策略和开发顺序是建议方案；分类细则、具体时间阈值和视觉样式留待后续验证。

## 一条完整体验

用户填入今天的安排，例如晚上七点到八点学习物理，再告诉 Yukio：“这段时间如果我连续二十分钟都在做其他事，就提醒我。”二十分钟仅为例子，是可修改的规则参数。

用户开启自动记录并完成必要授权后，Yukio 在约定范围内观察当前电脑活动。学习时段开始时先判断状态；已有物理学习线索时保持安静。持续识别到明确无关的活动才累计偏离时间，达到规则阈值后提醒。

提醒示例：“现在是你安排的物理时间，刚才一段时间似乎在看其他内容。要打开上次的资料吗？”提供“开始学习”“休息一会儿”“我在纸上学”“今天跳过”等操作，并实际调整后续行为。

晚上用户看到一段活动记录：“19:05—19:25，疑似物理学习，依据：前台课件标题。”用户可以把错误记录改成“其他课程”，也可以补充“19:30—20:00 在纸上做物理题”。自动观察时长不能直接称为有效学习时长，打开课件也不能自动判定任务已完成。

## 个性化页面里的三种信息

在同一个入口管理以下内容，但保存时区分用途和来源，避免一次活动被当成长期习惯。

| 内容 | 例子 | 如何产生和修改 |
| --- | --- | --- |
| 我的安排 | 今天七点学物理；工作日晚上有空 | 手动填写、自然语言生成草稿；后续再支持日历导入。明确行程是提醒的主要依据。 |
| 活动记录 | 刚才在看物理课件；一段时间无法识别 | 自动观察后合并成时间段，也可手动补记、改分类、改时间、删除。 |
| 我的偏好与习惯 | 喜欢温和提醒；这类网页属于物理资料；可能更常在晚间学习 | 用户明确设置的偏好直接生效；推测的习惯标注为建议或待确认，不覆盖明确设置。 |

每条自动记录尽量展示时间、来源、识别结果和简短依据；不展示模型内部推理。推测内容明确标为“可能”或“待确认”。用户不应被要求逐条确认普通活动记录。

自动记录与自动学习偏好分开控制：可以允许记录活动，却只手动维护长期偏好。手动模式仍可使用行程、普通提醒和手动补记。

## 行程怎样影响提醒

- 同时保留“固定时间提醒”“一段时间内根据状态提醒”和“关注变化后通知”三种用途，不强迫所有事情都有精确时间点。
- 优先级建议为：当前明确操作（暂停、休息、跳过）→ 当天手动修改 → 已确认的常规安排 → 自动推测的习惯。
- 当天改动默认只影响当天；改变每周常规安排时让用户看清作用范围。
- 行程有冲突时展示冲突，由用户选择优先事项；不同时催促用户执行两个互斥目标。
- 每次触发前重新检查行程是否已改、任务是否完成、是否处于休息或免打扰、是否刚提醒过。同一目标需要提醒冷却和次数上限，具体默认值待体验验证。
- 自动发现的习惯可以用于建议更合适的时间；第一版不自行改写已确认行程。未来可提供限定范围的自动调整，并保留变更说明与撤销。
- 兴趣简报属于可以延后的内容；已明确设置的截止时间提醒按各自规则处理，避免统一延后导致误事。

## 屏幕观察和活动记录

首次使用由用户明确开启自动记录、完成系统授权，并选择观察范围和是否在下次启动时继续。之后应用启动可按已保存设置恢复观察，并持续显示状态。关闭主窗口后是否继续观察需要在界面说明；建议与现有菜单栏驻留方式一致，提供随时暂停的入口，真正退出应用则停止观察。

先利用当前应用及能够取得的窗口文字等线索，信息不足时再考虑低频画面采样。不是所有应用都提供可读取文字；视觉识别需要支持图片输入的模型，纯文字 API 只能处理提取后的文字。采用本地文字处理、变化检测和缓存降低重复调用，不把持续视频上传作为第一版方案。

至少区分“与目标相关”“明确无关”“无法确定”和“暂停观察”。没有识别到物理内容不等于明确无关；调用失败、权限缺失、受限内容均不能计为分心。

锁屏、休眠和离开电脑时暂停偏离累计；返回后重新判断，不把离开期间算成违规。视频学习可能长时间没有键盘鼠标操作，因此无输入只是线索，不能单独证明用户离开。具体在场判断策略后续验证。

自动记录合并连续相近活动，保留简短摘要和必要依据，默认不保存原始截图历史。提供排除应用或窗口的范围控制；云端识别启用前说明可能发送的文字或画面内容，失败时不扩大采集范围。记录保留期限和清理策略在实现存储前确定。

## 用户纠正后发生什么

- 修改一条记录立即更新该条记录和相关统计；记录手动修改来源，自动处理不得再次覆盖。
- 将单次纠正应用到未来时，提供明确范围，例如“仅这段记录”或“以后将这个资料也识别为物理”。不把一次纠正泛化到整个浏览器或整个视频网站。
- 若错误记录影响了某条习惯推测，重新计算或撤回该推测；删除记录时同步处理基于该记录产生的未确认推测。
- 用户明确设置的偏好优先，禁止后台推测悄悄改回。提供“不要再推测这条偏好”的选择。
- 删除记录、删除偏好和关闭后续记录是不同操作，在界面说明各自影响。纠正和删除应作用于记录派生的检索摘要，避免被旧摘要重新引入。
- 第一版的个性化来自保存的偏好、资料归类和可控记忆，不需要训练一个专属模型。

## 页面与桌宠的分工

首页展示今天的安排、当前关注状态、下一项需要处理的事和已准备好的简报。当前状态应直白，例如“正在留意物理学习”“已暂停到八点”“暂时无法识别”。

“个性化”作为集中入口，内部先分为“我的安排”“活动记录”“偏好与习惯”。日常状态放首页，详细编辑放这里，避免同一内容出现两套保存逻辑。AI 提供方、模型与凭据配置留在设置中。

活动记录使用按时间排列的简短条目，点击后编辑分类、说明和时间；旁边能看到自动或手动来源。偏好同时区分已确认与建议，不让用户寻找哪些是自己填写的、哪些是助手猜的。

桌宠展示提醒小卡和简短回应；用户也可以用一句话添加或修改安排。对话产生的规则需要在页面里可见、可编辑，不只留在聊天中。

## AI、提醒和新闻的职责

AI 将自然语言变为结构化安排、识别活动主题、提出习惯建议、组织提醒措辞和摘要。应用负责验证规则、持久化、计时、适用时段、暂停、冷却和执行。AI 不直接控制无限制的提醒循环。

普通时间提醒在断网时仍按现有本地逻辑工作；依赖识别的条件提醒在证据不足时降级为未知，并说明状态。模型输出经过校验，旧行程或过期采样的判断不能触发新提醒。屏幕和新闻中的文字属于待分析内容，不能作为改变用户规则的指令。

新闻功能从真实来源获取内容，再由 AI 筛选、去重和总结，附来源、发布时间和获取时间。无新内容或获取失败时如实展示，不生成虚构的每日新闻。兴趣可手动选择，也可以由用户确认建议；一次浏览不自动形成永久订阅。

## 开发顺序与验证重点

1. **可手动使用的基础**：每日行程、关注目标、提醒规则和个性化页面；完善提醒可靠性。暂不依赖观察也能工作。
2. **AI 理解与活动记录**：接入 API，支持自然语言生成规则；在明确启用后采集有限范围的活动，允许查看、补记和纠正。先验证归类是否可用。
3. **完整的物理学习场景**：把行程、活动、持续时间和提醒连接起来；支持纸上学习、休息、跳过及冷却。先用指定资料和可解释归类，再扩展开放识别。
4. **长期个性化和兴趣简报**：积累可确认的习惯建议，接入新闻来源和投递时机；再考虑外部日历和其他能力。

后续实现至少验证：正常学习保持安静；明确无关活动达到阈值才提醒；未知或断网不算分心；暂停、休眠与离开不累计；手动改行程及时生效；纠正不会被自动覆盖；连续提醒受到限制。衡量提醒是否有帮助及误判是否易于纠正，而不只衡量产生了多少记录。

数据层分别维护行程、目标规则、活动记录、用户偏好和提醒投递记录，以稳定标识关联。它们共享服务，不把业务逻辑写入桌宠动画或各个页面。保留现有时间提醒数据的迁移与兼容方案，后续再确定详细结构和分类规则。
